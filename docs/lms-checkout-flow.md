# 수강신청·결제 안내·목록

2026-10-19, schema 202610190006.

수강생: `/courses` → `/apply` 또는 강의 신청 창 → `/checkout/{orderId}` → `/my-applications` → `/my-learning`. 신청은 로그인한 카카오·구글 계정에 저장하며 이름·이메일·연락처·소속을 미리 채운다. 이메일은 로그인 계정 기준으로 고정한다. 필수 동의는 직접 선택한다. 신청 완료 후 서버가 발급한 실제 주문 ID로 안내한다. 유효하지 않은 강의 주소는 다른 강의로 바꾸어 접수하지 않는다.

`/my-applications`에는 본인 주문만 표시한다. 강의명·주문번호 검색, 결제 상태 필터, 신청 상태와 금액, 결제 안내, 수강 화면 이동을 제공한다. 재신청한 경우 과거 주문은 이전 회차로 유지한다. `/checkout/{id}`는 본인 주문의 납부액·실제 확인 수납액·기수별 안내·입금 확인 요청을 제공한다. 취소·대기·이전 회차 주문의 결제를 유도하지 않는다. 카드·간편결제는 PG 연결 전까지 준비 중으로 표시한다.

관리자는 `/admin/cohorts`의 각 기수에서 결제 안내를 설정한다. 계좌·예금주·납부 기한·문의 방법은 확인된 내용을 입력한다. 설정이 없으면 담당자 안내 대기로 표시한다. 수강생이 실제 이체한 뒤 요청한 금액·입금자명·입금일은 `lms_payment_notices`에 저장한다. 주문당 한 번 접수하며 동일 요청 재시도는 중복 생성하지 않는다. 수정·분할 입금의 추가 확인은 담당자에게 전달한다. 이 요청만으로 결제 완료 기록이 만들어지지 않는다. 관리자는 `/admin/finance` 주문 상세에서 은행 증빙과 대조하여 기존 수납 기록 기능으로 확인한다.

관리자 `/admin/learning` 신청자 목록에는 신청 상태와 결제 상태·주문번호·입금 확인 요청 여부를 함께 표시한다. 신청 상태·기수·결제 상태·이름·연락처·주문번호로 필터링하고 현재 표시된 명단을 CSV로 저장할 수 있다. CSV는 사용자 입력의 수식 실행 접두사를 무력화하고 따옴표·개행을 보존한다. 금융 상세는 관리자·회계에게 연결한다.

취소·반려·회수 시 아직 입금/정산 기록이 없는 해당 회차 주문을 함께 취소한다. 이미 수납한 주문과 기존 결제·환불·정산 사실은 유지한다. 취소는 환불이나 은행 송금을 실행하지 않는다. 동시 요청은 기존 금융·정원 관리와 같은 DB 잠금으로 직렬화한다. 새 테이블은 본인 또는 관리자·회계에게만 SELECT를 허용하고 직접 쓰기는 서비스 키에도 차단한다. 서버 검증 RPC로만 요청을 접수한다.

## 공통 계좌이체 안내 (2026-10-19)

사용자가 지정한 수납 계좌는 NH농협은행 302-2154-5774-81, 예금주 이석호다. `lib/lms/payment-channel.ts`에서 공통 관리하며 신청 페이지·신청 모달에 `BankTransferNotice`로 표시한다. 복사 버튼은 하이픈 없는 계좌번호를 복사한다. 신청을 먼저 접수하고 주문 상세의 납부 가능 여부·남은 금액을 확인한 뒤 신청자 이름으로 입금하도록 안내한다.

신규 신청은 무통장입금 예정으로 기록하며 수납 완료로 간주하지 않는다. 기존 토스 결제 예정 주문도 현재 유효한 미결제 신청이면 계좌이체 안내와 입금 확인 요청을 사용할 수 있다. 대기·취소·이전 회차·검토 대기 주문에는 기존 결제 제한을 유지한다. 기수별 결제 안내가 있으면 우선 적용하고, 없으면 공통 계좌를 표시한다. 관리자 기수 설정에서도 이 기본 안내를 확인할 수 있다. 기존 주문·수납·환불·기수 안내 데이터는 일괄 변경하지 않는다.

카드·간편결제와 은행 자동 조회는 이 변경으로 활성화되지 않는다. 실제 입금 확인은 기존 관리자 수납 기록 절차를 사용한다.

## 비회원 접수 (2026-10-20)

`/apply`는 로그인 없이 이름·연락처·이메일과 필수 동의로 신청한다. 서버 전용 `lms_guest_application`은 인증 계정을 만들지 않고 별도 미가입 신청자 레코드, 기존 학습 신청, 주문을 한 트랜잭션으로 생성한다. 동일 이메일의 기존 회원과 자동 연결하지 않는다. 접수 요청 UUID로 재시도를 처리하며 해당 응답에는 이번 신청의 접수번호·금액만 반환한다. 비회원 완료 화면에서 확인서를 인쇄하고 입금 안내를 확인한다. 이후 `/guest-applications`에서 신청 이메일 인증으로 신청·결제 상태를 재조회한다. 신청 변경·취소는 접수번호로 담당자에게 문의한다. 관리자 `/admin/learning`에서 기존 신청과 함께 조회한다.

운영 반영에는 `supabase/migrations/202610200001_lms_guest_application.sql` 적용 후 앱 배포가 필요하다. 로컬 검증: `node scripts/test-lms-guest.mjs` (비회원 생성, 주문 원자성, 재시도, 정원 초과 롤백, 인증 계정 미생성, 익명·회원 직접 RPC 실행 차단).


## 비회원 신청 재조회 (2026-10-20)

`/guest-applications`와 `/api/lms/guest-lookup`을 추가했다. 신청 이메일로 6자리 번호를 발송하고 인증한 뒤 해당 이메일의 비회원 접수 주문만 조회한다. 기존 회원 신청은 포함하지 않고 계정 생성·연결도 하지 않는다. 기존 비회원 신청도 조회 대상이다. 신청 완료 화면·회원 신청 목록·사이드바에서 접근한다.

인증번호는 10분 유효, 5회 오입력 제한, 재발송 60초 간격·이메일당 15분 3회·접속 IP당 15분 10회를 DB에서 원자적으로 제한한다. 코드와 IP는 서버 HMAC, 조회 토큰은 SHA-256 해시만 저장한다. 조회 세션은 HttpOnly/Secure/SameSite=Strict 쿠키로 30분 유지하며 종료 시 서버에서도 폐기한다. API는 캐시를 금지하고 인증 없는 조회·외부 출처의 변경 요청을 거절한다. 새 발송 요청 시 하루 지난 인증 기록을 정리한다.

기존 Gmail SMTP 설정 `GMAIL_USER`, `GMAIL_APP_PASSWORD`를 사용한다. 사용자 승인 후 aiedu1 Vercel 운영 환경에 민감값으로 등록했다. 인증 메일은 신청 존재 여부와 관계없이 동일하게 발송해 이메일만으로 접수 여부를 노출하지 않는다. 발송 계정 연결은 메일 전송 없이 확인했다. DB 변경 파일은 `202610200002_lms_guest_lookup.sql`, 격리 DB 검증은 `node scripts/test-lms-guest-lookup.mjs`다.
