2026-10-19. Supabase schema 202610190005. 운영 진입점 `/admin/finance`; `/admin`, `/admin/settlements`, `/admin/crm`도 같은 콘솔을 사용한다. 수강생은 `/my-learning`에서 본인 결제 내역과 환불 요청을 확인한다.

## 데이터와 운영 절차

신규 수강신청과 주문은 같은 DB 트랜잭션에서 생성한다. 재신청하면 종전 주문은 보존하고 새 신청 회차의 주문을 만든다. 입금 확인은 실제 입금일·금액·증빙번호를 입력하여 기록한다. 주문 검토와 수강 승인, 실제 입금 확인은 각각 별개 작업이다. 토스페이먼츠 계약·키 연결 전에는 무통장입금/세금계산서 방식만 노출한다.

기존 브라우저 정산 저장소는 먼저 전체 문자열과 레코드를 수집한다. Supabase import 배치에 원문과 digest를 저장하고, 같은 ID의 상이한 원본은 충돌로 표시하여 보존한다. 원래 결제·정산 상태, 크레딧, 메모는 raw 필드에 유지한다. 기존 상태만으로 실제 결제나 정산 증빙을 만들지 않는다. 관리자 원본 검토 후 금액을 확정하고 실제 입금·환불·정산 증빙을 별도 입력한다. 기존 수강신청이 없는 자료는 관리자 수동 연결이 필요하다. 기존 localStorage는 삭제·초기화하지 않는다.

환불 요청은 처리 중 금액까지 합산해 잔여 결제액 이내로 제한한다. 관리자 결과 기록은 실제 이체 완료 후 사용한다. 전액 환불은 해당 신청 회차의 수강권 회수 옵션을 지원한다. 과거 주문 환불로 새 신청 회차의 수강권을 회수하지 않는다.

강사 정산은 확인된 순수납액에 지정 비율·공제율을 적용한다. 화면 기본값은 기존 시스템 값이며 계약·과세 판단을 대신하지 않는다. 확정 명세는 변경하지 않으며 이후 환불은 별도의 음수 조정 명세로 만든다. 지급·회수·상계는 실제 처리일·증빙번호로 기록한다. 은행 이체와 자동 환불은 실행하지 않는다.

## 권한·검증

관리자·회계만 금융/원본/정산 자료를 조회·변경할 수 있다. 운영 담당자는 CRM 연락처·상담 메모만 받는다. 수강생은 본인 주문·결제·환불만 조회하고 환불을 요청한다. 22개 테이블에 RLS를 적용했다. 금융 쓰기는 서비스 키 직접 DML도 차단하고 권한·중복·금액 검증 RPC만 허용한다. 모든 변경은 감사 로그에 남는다.

검증: 금융 DB 68개, 학습 DB 69개, 기존 기초 DB 74개, HTTP 41개 및 로그인한 관리자 금융 DTO/권한 검증. 운영 SQL에서 신청→주문→입금→부분환불→정산 조정을 트랜잭션 내 검증하고 전체 롤백한다. `scripts/export-lms-finance.mjs`는 22개 테이블을 `.local-data/backups`에 읽기 전용 백업한다. 백업에는 개인정보가 있으므로 Git과 배포에서 제외한다.
